长期以来，为了实现更好的收益 Uber 工程团队进行了广泛的努力，作为此举的一部分，最近我们团队专注于通过提高效率来降低计算的成本。其中一些最有影响力的工作是围绕 GO GC 优化的。在这篇博客中，我们希望分享我们使用一种高效、低风险、大规模、半自动化的 Go GC 调优机制的经验。

Uber 的技术栈由数千个微服务组成，这些服务由云原生的、基于调度程序的基础设施支持。这些服务大多数是用 Go 语言编写的。以前，我们的 Maps Production 团队，通过调整 GC 显著提高了多个 Java 程序的效率，在 2021 年初，我们探索了对基于 Go 的服务产生类似影响的可能性。我们抓取了几个 CPU profile 文件来评估当前的情况，我们发现对于绝大多数关键任务服务来说，GC 是最大的 CPU 消费者。下面是一些 profile 文件的示例，其中 GC（通过运行时的scanobject方法识别）正在消耗大量的计算资源。

## GOGC Tuner

Go 运行时会定期调用并发垃圾回收器，除非在此之前有事件触发了它。这些触发事件基于内存背压（memory back pressure），因此，更多的内存对受 GC 影响的 Go 程序是更有益的，因为它减少了 GC 运行的时间。此外，我们意识到我们主机的 CPU 和内存的比例是 1:5(1 核 CPU: 5GB RAM) 而大多数 Go 程序的比率是 1:1 或者 1:2, 因此，我们有信心可以使用更大的内存来减少 GC 对 CPU 的影响，这是一种服务无关的机制，如果谨慎使用，可以产生巨大的影响。

深入研究 Go 的垃圾回收机制超出了本文的范围，但以下是与这项工作相关的要点：Go中的垃圾回收是并发的，涉及分析所有对象以确定哪些仍然是可达的。我们将可达的对象称为 **“活动数据集（live dataset）”** 。Go 只提供了一个控制垃圾回收的开关，即 GOGC，以活动数据集的百分比表示。GOGC 值作为数据集的乘数。默认值是 100%，这意味着Go运行时将为新的分配保留与活动数据集相同数量的内存。例如

$$hard\_target = live\_dataset + live\_dataset * (GOGC / 100)$$
